# 真实数据采集

> 本文档是《开发文档》的 §14 部分；全部文档见 [docs/README.md](README.md)。
> 源码注释以 `§14.1` / `§14.2` 引用本文档。

本节回答一个问题：**库里那批数是怎么来的，凭什么说它是真的。**

它**不**重复 §3.2（数据层设计）和 [fetcher/README.md](../fetcher/README.md)
（怎么跑、参数、覆盖范围）已经说过的事。这里写的是那两处都不适合放的东西：
为什么把采集放在应用外面、以及这条路走下来踩到的坑。

---

## 14. 真实数据采集

### 14.1 采集在应用外面，是一个刻意的架构决定

`fetcher/` 是一段**开发期**的 Python 程序：在这台机器上跑、连 akshare 抓数据、
重新生成 `resources/macro.db`，然后把文件提交进仓库。它**不在安装包里、不在启动
流程里、不在 IPC 后面**。

这不是省事，是原设计的约束使然。这个应用的第一条安全边界是**完全不联网**：
渲染进程的 CSP 是 `connect-src 'none'`（`src/main/index.ts`），主进程没有任何
`fetch`（[§9.2](05-工程化与交付.md)）。把采集搬进应用，就要把这条边界拆掉——
而拆掉之后，每个装了它的人都会在自己的机器上直连统计局、东财和外汇局。

| | 采集在应用里（M1c 之前的方案） | 采集在应用外（现在） |
|---|---|---|
| 谁在发请求 | 每个用户的机器，每次启动 | 开发机，手动触发 |
| 采集礼貌性 | 每个用户都要守，且没法统一 | 只有一个人跑，天然低频 |
| 上游改接口 | 用户端静默写错值，没人知道 | 开发时当场发现，改完重新发布 |
| 数据来源可审 | 每个用户抓到的都可能不一样 | 仓库里那一份，`git log` 可查 |
| 代价 | — | 数据有「保质期」，要有人定期跑 |

最后一行是真实的代价：这份数据不会自己更新，最新期间停在上次跑的那天。
对一个看月度/季度宏观指标的工具来说，这个代价可以接受——**发布节奏本来就是
月度的**。但它意味着这件事**需要有人做**，不是自动的。

### 14.2 抓不到的东西：留空，不编，不绕过

三条规则，按优先级：

1. **没有免费源 → 不实现。** P0 的 23 个里有 5 个取不到（上游不发布，或渠道拿不到）。
   它们在库里是 `value=NULL`、`status='missing'` 的空行，界面上是「暂无数据」。
   每条留空在 `fetcher/macro_fetcher/mapping.py` 的 `UNSOURCED` 里带一句理由，
   **没有理由的空白不算数**——那是「忘了配」，不是「没有源」，测试会红。
2. **绝不编数。** 估一个「看起来合理」的值填进去，是这个项目最不能犯的错：
   那些数字会被截图、被引用，而没有任何痕迹说明它是编的。
3. **遇到访问控制，不绕。** 国家统计局对高频访问返回一个混淆过的 JS 挑战页
   （HTTP 200，内容是 `<noscript>Please enable JavaScript…`）。这是站点在表达
   「慢一点」，不是待攻克的技术障碍——逆向它属于对政府站点做访问控制规避。
   抓取器把它翻译成一句能读的话，让该指标单独失败，其余指标照常跑完。

第 3 条有一个直接后果：**那 5 条留空里有 4 条卡在同一个地方**。统计局的公开库
（`data.stats.gov.cn` 的新版接口）能通的时候，核心 CPI、固投累计同比、房地产投资
累计同比都能从那里取到；现在它一律返回挑战页，akshare 的通用接口同样取不到。
`mapping.py` 里为此留了一段给下一个接手的人的说明（三个参数怎么传、跨年份叶子
怎么合并、空值不能覆盖真值），**但没有写代码**——写了也跑不通，只会变成一段
看起来能用、实际每次都失败的路径。

### 14.3 换库那一次，不是修订

抓取器按 `(indicator_id, period, revision)` 比对写入：值变了就追加一条
`revision+1`、`status='revised'`，旧行保留。这是对的——修订历史是主键的一部分，
宏观数据本来就会被修订。

但**接手一份不是本工具写的库的那一次不符合这个模型**。它是换库，不是上游改了数。
不区分的话，每一处「旧值 → 真实值」都会被记成一次修订，于是：

- 界面上满屏「已修订」，读起来像统计局改了口径，而实际是我们在换掉一份旧库——
  这是**错误的信息**，不只是不好看；
- 修订历史里躺着一条旧值，看起来像「上一版的真实统计」。

第一次落盘实测产生了 2140 行这样的假修订。现在的判据是**库自己的内容**：
`fetch_log` 里还有不是本抓取器写的流水，就说明这份库来历不明，这一次按换库处理，
先清掉里面的旧观测，真实值从 `revision 0` 开始。本工具每次落盘都会
`delete_foreign_log`，所以清干净之后再跑就是正常的修订语义——那时候才是真的修订。

> 为什么不用一个 `app_meta` 标记位：标记位会被忘记设，也会被手工改成任何值，
> 而且它答的是「上一次跑的时候我以为这是谁的库」。流水答的是「这个文件里实际
> 发生过什么」——问法与 §14.4 那三步清理一致，也更严：手工拼出来的库同样认得出。

### 14.4 库里每一条观测都得有采集记录，所以清理必须彻底

「库里大部分是真实数据」这句话不成立：只要还有几条来路不明的值，应用那句
「真实统计数据」就是假的——横幅、图表署名、CSV 出处列会一起把它说出去。

第一次改造就在这里栽了：只清了 18 个已接入指标的合成基线，P1/P2 那 7911 行
（占全库 76%）原样留着，和改造前的内置库逐字节相同。发现它靠的是拿两个文件直接
比对，不是靠测试：**测试当时是绿的**——那时唯一的判据是一个写着 `real` 的标记位。

现在抓取器每次运行强制清理三步（观测 → 无源指标的旧值 → 来源不明的流水），
执行处与理由见 [§3.2.7](02-数据层.md)，看门人是 `bootstrap.test.ts` 里那条
「有值的指标必须能在 `fetch_log` 里找到采集记录」。三步都只登记、不删除，
真正的删除在落盘分支上，所以 `--dry-run` 能把它们如实打印出来。

### 14.5 界面必须跟着数据性质走，不能写死

> **本节已注销（2026-10-09，决策 16）。** 它整节的主张是「同一处界面文案要有两套
> 写法、按 `data_kind` 取」——那是合成库还在的时候成立的事。库里只剩真实统计之后，
> 两套写法里总有一套是死代码，而留着的代价是：任何一处写错分支都会让界面说出与库
> 不符的话，且**测试未必看得出来**（§14.4 记的那次就是）。
>
> 现在没有第二种数据性质，界面也就没有可分支的东西：出处声明是
> `@shared/provenance` 里的一个常量，界面手上的库与随包发布的那一份结构性地一致
>（[§3.2.0](02-数据层.md)）。原内容里仍然成立的两条事实——
> **导出的文件会脱离应用**（所以 CSV / PNG 必须带出处声明）、
> **老用户的旧库不用自己处理**（启动时就被覆盖掉）——分别落在
> `@shared/provenance` 与 §3.2.0。

### 14.6 发布日是推算的

库里 `released_at` **不是官方发布时刻**——统计局和东财都只给期间和值，不给时刻。
它是按各指标的惯例节奏倒推的，发布日历页从建立起就按这套规则排，不是这一轮
新引入的近似。规则一共八条（`fetcher/macro_fetcher/releases.py`）：

| 规则 | 日期 |
|---|---|
| `same_period` | 期间当天（日度序列） |
| `period_end` | 期末当天（PMI：当月最后一天上午出数） |
| `next_month_09` | 次月 9 日（物价：CPI / PPI 同日发布） |
| `next_month_15` | 次月 15 日（工业、消费、投资、外贸一组同发） |
| `next_month_20` | 次月 20 日（财政） |
| `this_month_20_weekday` | **当月** 20 日，遇周末顺延（LPR——当月值当月发布） |
| `quarter_next_month_16` | 季末次月 16 日（GDP） |
| `year_next_january_17` | 次年 1 月 17 日（年度序列） |

选法也是代码：LPR 按 id 前缀，日/季/年按频率，剩下按 `category` 查表
（`price → 次月 9 日`、`fiscal → 次月 20 日`、`sentiment → 期末`，其余次月 15 日）。
**哪个指标落在哪条上，以 `releases.py` 的 `rule_for()` 为准**——这里不列 23 行的
对照表，那会变成第二份会漂移的清单。

推算值在三处留痕，缺一不可：每次运行往 `fetch_log.message` 写一句「发布日为按惯例
推算，非官方发布时刻」（数据管理页把它显示在源名下面）；`app_meta` 里记
`release_rule_version`；本节列出规则本身。这一条不能省：`released_at` 一旦被当成
官方时间去核对，整个日历页的可信度就没了。

将来若接入统计局的发布库（`www.stats.gov.cn/sj/zxfb/`）拿到真实发布日，
应该写进一直空着的 `release_index` 表——那才是它的预期写方（§3.3）。
