# 系统架构与技术选型

> 本文档是《开发文档》的 §4–§5 部分；全部文档见 [docs/README.md](README.md)。

## 4. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 应用壳 | **Electron 44**（内置 Node 24） | 需求指定；Node 22+ 才有内置 `node:sqlite` |
| 构建 | **electron-vite** | 主进程/preload/渲染进程统一 Vite 构建，HMR 体验好 |
| UI 框架 | **React 19 + TypeScript 5**（`strict: true`） | 需求指定 |
| 图表 | **ECharts 6，按需引入（`echarts/core`）+ 自写宿主组件** | 中文生态最好；时间轴/十字准星齐全；Canvas 渲染优于 SVG。**不装 `echarts-for-react`**——理由见 §13 决策 12 |
| 样式 | **Tailwind CSS 4**（经 `@tailwindcss/vite`，无配置文件） | 无运行时开销；v4 起配置走 CSS 的 `@theme` |
| 本地数据库 | **`node:sqlite`（Node 内置）** | ✅ 已定；API 已实测验证，见下方说明 |
| 测试 | **Vitest**（node 环境，42 例） | 见 §10.3 |
| 打包 | **electron-builder `--dir`** | 生成未签名的本地 `.app`，自用足够；不签名、不公证、不做自动更新 |
| 类型检查 | `tsc --noEmit`（`npm run typecheck`） | 项目**没有配置 ESLint / Prettier** |

**本表以 `package.json` 为准，只写主版本号，不逐项誊抄依赖版本。** 选型表一旦兼做依赖清单就会跟 `package.json`
分叉——本节原先那版正是如此：列了 React Router、Zustand、TanStack Query、TanStack Table、
Radix、SheetJS、date-fns、electron-log、Playwright、ESLint/Prettier 共十项，**一项都没有装**。
`package.json` 里连 `dependencies` 键都不存在，全部在 `devDependencies`（渲染进程的依赖由
Vite 打进 bundle，主进程依赖由 electron-vite 的 `externalizeDepsPlugin` 处理，见 §10.4）。

> ✅ **SQLite 选型已定：使用 Node 内置的 `node:sqlite`**（决策见 §13）。
>
> **本地实测结论**（Node 23.11）：
> - 无需 `--experimental-sqlite` flag，`import { DatabaseSync } from 'node:sqlite'` 直接可用
> - 本项目所需能力全部具备：WAL 模式、复合主键、索引、**UPSERT（`ON CONFLICT DO UPDATE`）**、手工事务、预编译语句、命名参数
> - 零原生依赖 → **彻底消除 `electron-rebuild` 与分平台编译这一打包环节最大的坑**
>
> ⚠️ **唯一注意点：该 API 仍被标记为实验性**（运行时会打印 `ExperimentalWarning`，提示"might change at any time"）。因此必须：
> - 所有 SQLite 访问一律经 `src/main/db/adapter.ts` **单一封装**，业务代码绝不直接 `import 'node:sqlite'`
> - 这样 API 一旦变动、或需换回 `better-sqlite3`，都是**单文件改动**
> - 在启动入口抑制该警告，避免污染日志
> - **升级 Electron 前必须先跑通全量测试**（Node 版本随 Electron 升级而变）

## 5. 系统架构

### 5.1 进程模型与安全边界

```
┌───────────────────────────────────────────────────────────────┐
│ 主进程 (Node)                                                  │
│  · SQLite 读写（全部经 db/adapter.ts）                         │
│  · 内置数据文件的摆放（首次复制 / 重置覆盖）                   │
│  · 无网络请求、无采集、不生成数据（M1c / M1d 起）              │
└───────────────────────────┬───────────────────────────────────┘
                            │  ipcMain.handle / ipcRenderer.invoke
                            │  （全部结构化：{ok:true,data} | {ok:false,error}）
┌───────────────────────────┴───────────────────────────────────┐
│ preload（contextBridge，白名单 API）                            │
│   window.macro = { listIndicators, getSeries, refresh, ... }   │
└───────────────────────────┬───────────────────────────────────┘
                            │
┌───────────────────────────┴───────────────────────────────────┐
│ 渲染进程 (React)                                               │
│  · 纯 UI，不直接访问网络、不直接读文件                          │
│  · ECharts 渲染                                                │
└───────────────────────────────────────────────────────────────┘
```

**安全基线（`BrowserWindow` 配置）：**

```ts
webPreferences: {
  preload: join(import.meta.dirname, '../preload/index.cjs'),
  contextIsolation: true,     // 必须
  nodeIntegration: false,     // 必须
  sandbox: true,              // 必须
}
```

⚠️ **两处容易照抄错的地方**：主进程是 ESM（`"type": "module"`），**没有 `__dirname`**，
所以用 `import.meta.dirname`；preload 的产物后缀是 **`.cjs`** 而不是 `.js`——sandbox 下的
preload 必须是 CommonJS，`electron.vite.config.ts` 里专门为它设了
`output: { format: 'cjs', entryFileNames: '[name].cjs' }`。写错任一处都是启动即失败。

**CSP（渲染进程）：** 生产环境一共 8 条指令（`src/main/index.ts` 的 `CSP_PROD`）：

```
default-src 'self'; connect-src 'none'; img-src 'self' data:;
style-src 'self' 'unsafe-inline'; script-src 'self';
object-src 'none'; base-uri 'none'; form-action 'none'
```

`connect-src 'none'` 意味着**渲染进程完全无法发起网络请求**，所有数据必须经主进程。这既是最佳实践，也保证了「数据只在主进程碰」这个架构约束不会被无意破坏——M1c 之后主进程自己也不联网了，这条约束仍然生效，只是当前没有东西要去违反它。

> ⚠️ **dev 下有一条例外。** `CSP_DEV` 把 `connect-src` 放宽成
> `'self' ws://localhost:* http://localhost:*`，否则 Vite HMR 连不上。
> 所以「渲染进程完全无法发起网络请求」**只对打包产物成立**——要验证这条得看 `.app`，
> 在 `npm run dev` 下看到网络请求不算破例。

### 5.2 IPC 契约

> **唯一事实源是 `src/shared/types.ts`**——本节照抄它的 `MacroApi`，通道名在同文件的
> `IPC` 常量里。加方法时改那里，不要只改文档。

```ts
export type Result<T> =
  | { ok: true;  data: T }
  | { ok: false; error: { code: string; message: string } };

export interface MacroApi {
  listIndicators(): Promise<Result<Indicator[]>>
  getSeries(req: { id: string; from?: string; to?: string }): Promise<Result<Observation[]>>
  getDataStatus(): Promise<Result<DataStatus>>
  refresh(): Promise<Result<RefreshResult>>
}
```

目前就这四个。两点值得注意：

- **`refresh` 的语义不是「去网上抓」**，而是「把示例数据恢复到初始状态」——界面上那个按钮
  写的是「重置示例数据」（§3.2.0）。
- 每个方法都返回 `Result<T>` 信封，不抛异常：渲染进程收到的失败是一条**可显示的消息**，
  而不是一个未捕获的 rejection。

概览、日历、导出、设置这些接口**尚未实现**，等做到时再加进 `MacroApi`，本节不预先罗列。

> ⚠️ **`resources/macro.db` 是二进制产物，git diff 看不到它的变化，也没有生成器能重建它。**
> 它被改动时（无论被谁、被什么工具）在 `git status` 里只是一个「二进制文件已修改」。
> `bootstrap.test.ts` 里那组「产物结构」断言是唯一的守门人。

**这就是实际目录**，不是目标形态——树里每一个文件都存在。M2 之后的页面目录（`pages/` 等）尚未创建，等真正动手时再加进来。

> ★ **`src/shared/indicators.ts` 是指标元数据的单一事实源。** UI 与测试全部从它读取指标定义，
> 不存在第二处定义。（原计划拆成 `indicators.json` + 类型化封装，实际直接写成 `.ts`——
> 有类型检查、不必再包一层，且 `note` 这类长文本放在 `.ts` 里可读性更好。）
>
> ★ **测试与源码同目录**（`db/migrate.test.ts`、`charts/lineOption.test.ts`），不设 `tests/` 顶层目录：
> 改一个模块时，它的测试就在旁边。原计划的 `tests/fixtures/` 随采集器一起删除了（§10.3）。
