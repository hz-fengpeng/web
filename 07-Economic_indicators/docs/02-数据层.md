## 3. 数据层设计

> 这一节决定项目的成败。UI 做得再漂亮，数据层不稳，应用就是个玩具。

### 3.1 数据源调研

>
> 那一轮调研之后，采集改成**全部经 akshare**，自己解析的那套适配器整个删掉了——
> 结论因此不再是「哪个接口怎么拼」，而是「哪个接口的哪一列」。现在的事实源是
> `fetcher/macro_fetcher/mapping.py`（每条规则的出处）与
> `fetcher/macro_fetcher/sources/akshare_src.py`（为什么不再自己解析）；
> 跑法与覆盖范围见 [fetcher/README.md](../fetcher/README.md)。
>
> 仍然成立的一条：统计局的公开库对高频访问返回 JS 挑战页，**不绕过**

数据版权归原发布机构所有。

### 3.2 数据来源：内置的真实统计数据库文件

> ⚠️ **库里的数值是真实统计数据**，由国家统计局、东方财富、国家外汇管理局、中国债券信息网
> 与新浪财经的公开数据
> 经 `fetcher/` 离线抓取后写入。界面上有一条常驻横幅说明出处与边界（「不是实时行情」、
> 「少数指标暂无免费数据源，以缺失如实呈现」）。
>
> 数据是一份随项目提交的 SQLite 文件 `resources/macro.db`（109 个指标、10251 条观测，
> 其中 23 个指标有值）。
> 应用运行时**不生成任何数据、不联网**：每次启动只是把它复制到 `userData`。

**「真实」这个词在这里有确定的含义，不只是来源标注**：库里每一条 `value IS NOT NULL`
的观测，都能在 `fetch_log` 里找到对应的那一次采集；没有免费源的指标留的是
`value=NULL` 的空行，不是编出来的数。这条不变量由 `bootstrap.test.ts` 守着，
执行它的是抓取器的 `_plan_unclaimed`（见 §3.2.7）。

#### 3.2.0 当前实现：内置数据库文件 + 每次启动覆盖

**数据从哪来**：`resources/macro.db`，随项目/安装包一起发布。应用不生成它，
**每次启动都把它覆盖到 `userData/macro.db`**，界面读的一直是这份副本。
摆放与重置都在 `bootstrap.ts`：启动和「重置数据」走的是同一个原语 `restoreUserDb`。
抓取本身在 `fetcher/`（Python + akshare），**不在应用里运行**——
每个用户不会因为装了它就去直连统计局，见 [fetcher/README.md](../fetcher/README.md)。

**为什么是复制而不是直接打开内置文件**，两个理由缺一不可：

1. **迁移要写。** `migrate()` 要写 `app_meta.schema_version`，日后 schema 变更也要写。
   只读打开无处可写；可写打开则是往应用包内部写——打包后那是 `.app` 的一部分。
2. **程序与数据分开。** 放 userData 是 Electron 的惯例：安装包只读，
   运行期该可写的东西写在用户目录下。

**为什么每次都覆盖是安全的**：应用从不写 `observation`。运行期唯一会写库的是
`migrate()` 记的那个 `schema_version`。那份文件因此只是内置库的一个运行期副本，
不是「用户的数据」——覆盖它不丢任何东西，换来的是「界面手上的库就是随包发布
那一份」这条**结构性**保证：界面写的来历与库里的内容不可能对不上，不必再去读
一个可能被改坏、也可能忘了写的标记位。代价只在「运行期用 `sqlite3` 手工改过库」
的场合出现，而那有「重置数据」按钮当场恢复，下一次启动也会自己回到内置那份。

**路径怎么定**（`index.ts` 的 `dbPaths()`）：dev 用 `app.getAppPath()/resources/macro.db`；
打包后用 `process.resourcesPath/macro.db`——因为打包后主进程代码在 `app.asar` 里，
用 `app.getAppPath()` 拼 `resources/` 会指进 asar 内部。`electron-builder.yml` 的
`extraResources` 负责把文件放到那个位置。**这两处必须同时正确**，漏一处就是启动即失败。

**「重置数据」按钮的语义**：`IPC.refresh` → `resetToBundled()` → 关连接、覆盖
userData 那份回内置状态。它做的事和启动时**完全一样**，只是不用重启——
用户在用 `sqlite3` 改坏库之后，靠它立刻回到出厂状态。

> ⚠️ **重置必须先关连接**，顺序错了会**静默失效**——不抛错、返回值正常，但一行都没换。
> 机制：`copyFileSync` 就地截断写、inode 不变，旧连接并不指向已消失的文件，它仍持有
> 自己的 WAL；覆盖之后 SQLite 把那份 WAL 重放回去，于是新连接读到的是「旧数据 +
> 旧连接的后续写入」，内置文件被整个盖掉。`bootstrap.test.ts` 里有一个**反例测试**
> 专门断言这个行为，把这个坑钉住。

**核心约束：库是整份声明的**（本节开头那条不变量；执行处见 §3.2.7 与 §14.4）。
界面上说得出「这批数从哪来」的地方有四处，每一处都与库直接同源：

| 防线 | 做法 |
|---|---|
| 界面 | 顶部常驻出处条：数据来源与两条边界（不是实时行情、少数指标暂无免费数据源） |
| 数据源名 | `REAL_SOURCES` 列国家统计局 / 东方财富 / 国家外汇管理局 / 中国债券信息网 / 新浪财经（★ 与 `fetch_log.source_id` 逐字一致，测试直接拿这张表去查流水） |
| 导出 | CSV / PNG 里的出处声明取自 `@shared/provenance` 的同一个常量；主进程校验 CSV 里有没有它 |
| 采集日志 | 数据管理页的源健康度直接读 `fetch_log`，读不到记录就显示「从未采集」 |

**文件里的数据长什么样**（`fetcher/` 抓取的实测形态）：

- 日度 `YYYY-MM-DD`、月度 `YYYY-MM`、季度 `YYYYQn`、年度 `YYYY`；期末日期用于跨频率排序。
- 月/日序列 2021 年 9 月起；季度到 2026Q2，日度（中间价）随交易日推进（本文写作时到 2026-10-09）。
- 1—2 月的口径**逐指标不同**（合并 / 各自单列 / 两个月都没有），谁是哪一种以
  `mapping.py` 的 `jan_feb` 为准——这里不再抄一份会漂移的清单，见 §3.4 第 1 条。
- 日度汇率只在**银行间市场交易日**有行：跳周末，也跳法定节假日（实测 2021/2022/2024/2025
  的国庆与春节窗口一条都没有）。这一点与原示例库不同——那里只跳周末。
- **一条 `revised` 都没有**。23 条已接入序列的上游都是发布即终值；修订要等抓取器后续
  运行才可能出现。也就是说，App 里 `prelim` / `revised` 两个状态的渲染分支**不再被这个
  文件覆盖**，改动它们时不能指望跑测试报警（`bootstrap.test.ts` 里写明了这件事）。
- 86 个无源指标各有一串 `value=NULL` / `status='missing'` 的空行，覆盖与有源指标同一段
  期间网格（按各自的频率：月度 / 季度 / 年度）。它们是**声明**——「这些期间该有值而我们
  没有」，与「未纳入采集、连行都没有」是两回事（§3.2.7）。登记全部 109 个指标之后，
  库里已经没有「未纳入采集」的指标了，`_plan_unclaimed` 只对**目录外的 id** 生效。
- 发布日是按惯例**推算**的，不是官方发布时刻——规则全集与选法见 §14.6。
  `fetch_log.message` 里每次都写明这一点。

**不再有采集礼貌性问题**：抓取跑在开发机上、手动触发，每个用户的机器不会直连任何站点。
渲染进程的 CSP 是 `connect-src 'none'`，主进程也没有任何 `fetch`。

#### 3.2.7 「库里每一条观测都必须是真实的」怎么执行

这一条是整份改造的立身之本，也是最容易自己骗自己的地方——第一次改造就踩了：
只清了 18 个已接入指标的合成基线，P1/P2 那 7911 行原样留着（和改造前的库逐字节相同），
而 `data_kind` 已经写成 `real`。界面、图表、CSV 一起对着 76% 的合成数据说「真实统计数据」。

现在由抓取器每次运行强制执行三步（都在 `fetcher/macro_fetcher/cli.py`）：

| 步骤 | 清什么 | 为什么连「留着反正界面会标」都不行 |
|---|---|---|
| `_plan_unclaimed` | 观测：既无取数规则、也不在 `UNSOURCED` 里的指标 | 「这些数都有来路」说的是**整个库**，留几条没来路的就是让它变成假话（§14.4） |
| `_plan_unsourced` | 无源指标里的**旧值**（只数 `value IS NOT NULL` 的行，空行保留） | 空行是一条声明；有值就说明那是上一次留下的、没有采集记录的 |
| `_plan_foreign_log` | `fetch_log` 里 `source_id` 不在采集范围内的流水 | 那条「内置示例数据文件 · 10465 条」的记录会让每个打开库的人怀疑整库 |

三步都**只登记、不删除**：真正的删除在落盘分支上，所以 `--dry-run` 能把它们如实打印
出来，而不是承诺一个它没有模拟的动作。没有「保留」的开关——留一个「保留这些值但仍然
声称是真实库」的开关，就等于留了一条自我欺骗的路。

> ★ `_plan_foreign_log` 判「合法来源」用的是规则表的**全集**，不是本次跑到的那些：
> `--only cn.cpi.yoy` 时只有 eastmoney 在跑，按「本次的源」判断会把 nbs / safe 的
> 采集记录一起删掉，而报告里写着「清除 2 条」——看起来还挺合理。

### 3.3 数据库 Schema

SQLite，单文件。**关键设计：`period` 用于标识期间，`period_end` 用于排序与对齐。**

**表结构以代码为准**：v1 基线是 `src/main/db/schema.sql`（已冻结，只负责把空库建成 v1），
其后一切变更一律追加到 `src/main/db/migrate.ts` 的 migrations 数组。这里只记设计取舍，
不再誊写建表语句——誊写过的 schema 图迟早会跟代码分叉，本节原先那版就列了 8 张表，
而实际只有 4 张。

| 表 | 作用 |
|---|---|
| `observation` | 观测值。主键 `(indicator_id, period, revision)`，索引 `(indicator_id, period_end DESC)` |
| `fetch_log` | 数据来源健康度日志，驱动页脚的源状态显示；也是「有值的观测都有采集记录」那条例据的另一半（§3.2.7） |
| `app_meta` | 键值对：`schema_version`（表结构）、`last_fetch_at`（页脚「最近采集」）、`data_sources`（★ **本次运行**用到的源，不是「库里有数据的源」；源健康度读的是 `fetch_log`）、`fetch_tool`、`release_rule_version`、`unsourced_indicators`（86 个 id） |
| `release_index` | 发布页索引，v2 迁移建立（§3.3.1）。**当前是空表**——见 §3.3.1：它从建立起就没有过写入方 |

**指标元数据不在库里**，在 `src/shared/indicators.ts`——它是 `listIndicators` 的唯一事实源。

**Schema 设计要点：**

- `period` + `period_end` 分离 → 提供日/月/季/年的排序与定位；对比页仍严格限制同频率，不把不同口径混画。
- `revision` 进主键 → GDP 有初步核算/初步核实/最终核实三次修订，社融信贷月度修订。**修订历史必须保留**，不能直接覆盖。
- `status` 区分初值/修订值 → UI 上给修订值加标记。（M1a 起 `status` 共五态：`ok | prelim | revised | missing | merged`。UI 用**中文文字标签**呈现，映射表是 `Record<Observation['status'], string>` 的穷尽类型——漏一个编译期就报错，不会再出现直接印英文 `merged` 的情况。）
- `note` 字段承载口径说明 → 这是本产品相对同类工具的核心差异化，必须在 UI 显著位置展示。

#### 3.3.1 迁移机制（M1a 建立）

**`schema.sql` 就此冻结为 v1 基线**，文件头已写明；其后一切 schema 变更走 `src/main/db/migrate.ts`，`schema.sql` 只负责建空库。

```ts
const BASELINE_VERSION = 1        // schema.sql 建出来的版本
interface Migration { version: number; label: string; up: (db: Db) => void }
// 模块加载时校验 version 连续（必须是 BASELINE_VERSION+1+i），断了就直接抛
export const SCHEMA_VERSION = …   // 取最后一个迁移的 version
export function migrate(db: Db): { from: number; to: number; applied: string[] }
```

`migrate()` 读 `app_meta.schema_version`：

| 库中记录 | 行为 |
|---|---|
| 缺失 | 视为 v1（M0 装机的库就是这种），顺序补齐 |
| < `SCHEMA_VERSION` | 顺序补齐，**每个迁移单独一个事务** |
| = `SCHEMA_VERSION` | 什么都不做 |
| > `SCHEMA_VERSION` | **抛错拒绝打开**——绝不按旧 schema 去读写一个更新的库 |
| 非法值 | 抛错，**不静默当成 0 重来** |

⚠️ **建这个机制时踩到的坑（M0 遗留）：** `initDatabase()` 里有一句无条件的 `setMeta(handle, 'schema_version', '1')`，**每次启动都把版本号压回 1**，等价于没有版本记录。M0 期间它被 `CREATE TABLE IF NOT EXISTS` 完全掩盖，看不出任何症状；但只要写出第一个 `ALTER TABLE ADD COLUMN`，就会变成**每次启动都抛 `duplicate column name`**。这句话已删除。

v1 → v2 的内容是建 `release_index`（`url` 主键，另有 `source_id`、`title`、`published_at`、`page`、`fetched_at`）——原为 M1b 的发布索引准备，但 M1b 已暂缓、采集层又整体删除，**所以这张表从建立起就没有写入方，一直是 0 行**。它是迁移机制的第一个真实用例，本身留着无害。

**真机验证（2026-09-25）：** 拿 M0 装机现场的库（`schema_version=1`、20 条观测、无 `release_index`）启动，日志输出 `v1 → v2：v2 release_index`，重启后输出 `v2（已是最新，期望 v2）`，20 条观测原样保留。


### 3.4 数据口径陷阱（必须在实现中处理）

这一节是本项目最容易出错的地方，逐条对照实现。

| # | 陷阱 | 处理方式 |
|---|---|---|
| 1 | **1-2 月合并发布** | 统计局因春节错月，1 月和 2 月的数据会合并发布，所以某个指标**没有 2026-01** 可能是**正常**的，不要一律报缺失。**这不是一条通用规则，而是每个指标各选一种口径**，在 `mapping.py` 的 `jan_feb` 字段上声明（哪个指标是哪种，以那里为准）：`MONTHLY` 1、2 月各有当月值（CPI / PPI / PMI / 失业率，实测库里各有 5 个 1 月观测值）；`MERGED` 1—2 月并成一条挂在 2 月，`period='YYYY-02'`、`status='merged'`，UI 显示「1—2月合并」（社零、财政收入）；`GAP` 源对两个月都不给当月值，只有累计序列里有（工业增加值）。★ **通用豁免两个方向都错**：给 CPI 挂 `MERGED`，它每年 1 月的观测会凭空消失且没有任何症状；给工业增加值挂 `MONTHLY`，则是要求源给出它根本没有的值，于是每次都「抓不到」。规则与源的**实际行为**不一致时抓取器**报错退出**，不静默丢数据（`cli.py` 的 `_apply_jan_feb`）。⚠️ 原方案是「在 `note` 标注」，但 `note` 在 `indicator` 上、不在 `observation` 上，走 note 需要改表；改用 `status` 是更轻的路径。 |
| 2 | **累计值 ≠ 单月值** | 固投、社零、财政收入在年内公布的是**累计同比**。`valueType` 必须准确，图表 Y 轴标题必须写明"累计同比"。 |
| 3 | **同比 / 环比 / 累计同比是三个指标** | 拆成独立的 `indicator` 记录（库里现成的例子是 `cn.ind_prod.yoy` 与 `cn.ind_prod.mom` 这一对），**绝不混画一张图**。 |
| 4 | **季调 vs 未季调** | GDP 当季**环比**是季调后的，当季同比不是。`seasonalAdj` 标记，UI 在图注写明。 |
| 5 | **基期轮换** | CPI 每 5 年轮换基期（2021–2025 用 2020 年基期）。跨基期的长序列严格来说不可直接比较，`note` 需说明。 |
| 6 | **数据修订** | 保留 `revision`，UI 在数据表里标注"已修订"，并用虚线或角标标出。 |
| 7 | **双单位口径** | 进出口同时有美元和人民币口径；M2 单位是"亿元"。`unit` 字段必须准确，禁止跨单位同图。 |
| 8 | **发布滞后** | CPI / PPI 次月 9 日、PMI 当月最后一天、GDP 季末次月 16 日（库内实测：2026Q2 → 2026-07-16）——**举例而已，规则全集见 §14.6**。同一「月份」的指标并非同时到齐，看板上的最新一期因此可能长短不一——这是发布节奏，不是数据缺失。 |
| 9 | **累计值换算** | 若需从累计同比推算单月同比，注意这是**近似计算**，且 1-2 月无法拆分。若做此换算，必须标注为"计算值"。 |
| 10 | **时区与日期** | 发布时刻用北京时间；`period_end` 用自然月末，不用"第几周"。 |

> ⚠️ **上表是「要求」，不全是「现状」——有两处是缺口，读的时候别当成已实现：**
>
> - 第 2 条的后半句「图表 Y 轴标题必须写明累计同比」：`lineOption.ts` 的 `yAxis` **没有 `name`**，
>   图上任何位置都没写「累计同比」。目前只有详情页的口径说明（`note`）和单位能传达这件事。
> - 第 6 条的后半句「用虚线或角标标出」修订值：**没有做**。图上只有 `merged` 有菱形点，
>   修订值（`status='revised'`）在图上没有任何标记，只有切到数据表才看得到「已修订」。
>
> 其余各条与实现一致。
